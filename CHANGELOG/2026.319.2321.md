### 1. ONE composite-key split

`parseCompositeKey` special-cased `charly/secret/` and `charly/enc/`, then cut every OTHER service at the
**first** slash. Every writer in the tree cuts at the **last**: `collectCredentialNames` (the index reader
behind `list`/`export`), `sdk/deploykit`'s `CollectCandySecretAccepts` + `EnsureCandySecret`, and
`plugin-deploy-pod`'s `secretKeyForDep`. A Secret Service item's identity IS its D-Bus
`(service, username)` attribute pair, so for the namespace the skill itself recommends —
`charly/api-key/<name>` — the config-side reader looked for `(charly, api-key/<name>)` while the writer
had stored `(charly/api-key, <name>)`.

The prefix table is **deleted**; `parseCompositeKey` is last-slash for every service, and
`collectCredentialNames` calls it instead of re-implementing the split (one implementation, R2).

### 2. `migrate-secrets` keeps the shadow index it writes

The loop migrates through `KeyringStore.Set`, which appends the shadow-index entry to `config.yml` and
saves. The trailing save then wrote back the `RuntimeConfig` captured BEFORE the loop, so every index
entry the migration had just added was dropped — leaving the credentials in the keyring with nothing
pointing at them, and `list`/`export` (both index-driven) reporting "no entries" over a store that held
them. `stripMigratedPlaintext` now saves through ONE read-modify-write over a **fresh** load and deletes
**exactly** the pairs that reached the keyring, so an entry whose write FAILED also keeps its plaintext
(the old wholesale `VncPasswords = nil` stripped those too).

### 3. `charly secrets prune [--dry-run]`

Both the `KeyringStore.Get` drift warning and the doctor's message already told operators to run this verb;
it did not exist (`plugin-secrets: parse 'charly secrets [prune]': unexpected argument prune`, rc=1). It
drops shadow-index entries that resolve in no healthy collection, never reads or writes a value, and — the
safety property — treats an unreadable or locked keyring as an ERROR, never as "the credentials are gone".

### 4. Writes and deletes resolve the collection like reads do

`Set`/`Delete` went through `zalando/go-keyring`, whose Linux provider resolves ONE collection
(`/collection/login` when it exists, else the `default` alias path) and ignores `keyring_collection_label`.
Reads iterate `default → keyring_collection_label → every healthy collection`. So the documented pin held
on reads only, and `charly secrets delete` of a credential living in any other collection printed
`Deleted … from keyring`, dropped its index entry, and left the item in the store.

Both now go through the `ssClient` the reads use — `resolveTargetCollection` + `createItem(replace=true)`,
and `findItemByAttrsAcrossCollections` + `deleteItem` — i.e. the primitives this plugin already built and
already wired for the GPG keystore path, which had zero callers on the credential-store path. `go-keyring`
has no caller left, so the dependency is gone from `go.mod`, and the three prose surfaces that said it
"lives here" (package comment, candy description, README) are corrected in the same commit.

## Change classification

**Runtime library fix + one new CLI verb (plugin code, no schema change).** `schema/credential.cue` and
`params/` are untouched: `prune` is CLI-side reconciliation and adds no `verb:credential` method, so the
provider wire contract is unchanged.

Consumer impact: `verb:credential` request/reply shapes are byte-identical; every existing `charly secrets`
verb keeps its name and output; `prune` is additive. Behaviour changes are the fixes themselves — a
two-segment service now resolves at the identity its writer used; `migrate-secrets` no longer loses the
index; writes land in the collection the reads start from.

**Breaking change + rollback:** none for consumers — no wire shape, verb name, env var or config key
changes, and the one dependency removed (`go-keyring`) has no caller left. The closest thing to a
behaviour change is that a new secret now lands where reads start (`default` alias, then
`keyring_collection_label`, then the first healthy collection) instead of in ONE client-chosen collection;
credentials already stored elsewhere stay readable (the read path iterates) and are now deletable (the
delete path iterates). Rollback is `git revert` of the squash: the index file and the keyring are data, not
code, and neither is rewritten destructively by this change (the migration still keeps a
`config.yml.bak`).
